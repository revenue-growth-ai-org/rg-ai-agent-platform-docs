# Platform Repo Audit — 2026-09-07

Scope: the five Revenue Growth AI Agent Platform repos, audited against the
state of `main` plus each local working tree. `4-rg-ai-agent-platform-chat` is
**not** part of this audit — it is a separate project, deliberately left
untouched: no branch was created there and no finding about it is recorded here. Goals were narrow: correct inaccurate
documentation, and remove redundancy. Not a rebuild — the platform is in
production for its first customer. Deliberately no account ID here: these
repos are meant to deploy into any customer's own AWS account.

**Audit scope exclusion:** `3-rg-ai-agent-platform-agent/app/agents/` was
declared out of scope by the repo owner during this audit and was not read,
edited, or committed. `app/scan_scaffolding.py` was also left untouched because
it carries uncommitted v2 work (see Tier 4 §T4-1).

Where a doc and the code disagreed, the running code was treated as the source
of truth, and that is stated explicitly in each finding.

## Tier 1 — Wrong and actively misleading

### T1-1 · `external_secrets_arns` does not exist, but the tfvars examples still set it

`3-rg-ai-agent-platform-agent/variables.tf:163` declares the real variable:

    variable "external_secrets" {
      type        = map(string)

There is no `external_secrets_arns` variable anywhere in the repo's `.tf` files.
Yet it is still set in the two example files a new customer is told to copy:

- `3-rg-ai-agent-platform-agent/prod.tfvars.example:29` — `external_secrets_arns  = []`
- `3-rg-ai-agent-platform-agent/cost_optimized.tfvars.example:21` — `external_secrets_arns  = []`

and still documented as the mechanism in:

- `3-rg-ai-agent-platform-agent/README.md:30` — "add secret ARNs to external_secrets_arns"
- `3-rg-ai-agent-platform-agent/README.md:121` — "add the ARNs to external_secrets_arns in tfvars"
- `3-rg-ai-agent-platform-agent/TROUBLESHOOTING.md:33` — "Verify the ARN is also listed in external_secrets_arns in tfvars"

**Correction to a prior claim.** `setup.sh:11-12` asserts this "fails
`terraform apply` with an 'Unsupported argument' error." That is not what
Terraform does. An undeclared variable supplied in a `-var-file` produces a
*warning* ("Value for undeclared variable") and is otherwise ignored. The real
failure mode is worse than a hard error: the secret ARNs are silently dropped,
the agent's IAM policy never grants access, and the failure only appears at
runtime when `get_secret()` cannot read the credential.

Planned action: **FIXING** — docs and both `.tfvars.example` files corrected to
`external_secrets` map syntax. Behavior-preserving: `external_secrets_arns = []`
and `external_secrets = {}` both result in no external secrets being wired.

### T1-2 · Agent README documents a mechanism that no longer exists

`3-rg-ai-agent-platform-agent/README.md:117-122`, "Implementing agent logic":

> 1. Edit app/agent.py — replace the placeholder execute() function with your agent logic

The current contract is `async def run(request, logger)` in
`app/agents/<name>.py`, staged to `app/business_logic.py` at build time
(`.gitignore:34-36`: "Build-time staging file — regenerated from
`app/agents/<agent_name>.py`"). A reader following this section edits the wrong
file with the wrong function signature.

Planned action: **FIXING** — section rewritten to the real mechanism.

### T1-3 · `CLAUDE.md` is cited as authoritative but exists in no repo

Verified absent from all six repos via the contents API and on disk. Cited as
binding in five places:

- `rg-ai-agent-platform-docs/CUSTOMER-INSTALL-DEBUGGING.md:466` — treats it as a

  as already fixed and numbered".

(Five further citations exist in `4-rg-ai-agent-platform-chat`, which is out of

Every one of those cross-references resolves to nothing. A future session told
to "follow CLAUDE.md §2a" has no way to comply.

Planned action: **ASK** (see T4-2). The file most likely lives in a Claude
Project's custom instructions rather than git. Committing it is the owner's

### T1-4 · Production agent business logic is not in version control

`3-rg-ai-agent-platform-agent/app/agents/` on disk holds seven business-logic
modules plus four scan tasks; `main` has three files. Untracked, ~270 KB:
`deal-auditor.py` (80 KB), `deal-coaching.py` (49 KB), `researcher.py` (42 KB),
`company-health.py` (41 KB), `daily-report_scan_task.py` (36 KB),
`company-health_scan_task.py` (16 KB), `deal-auditor_scan_task.py` (7.9 KB),
plus `app/scan_task.EXAMPLE.py`.

This is not deliberate. `.gitignore:30-36` ignores only the *generated*
`app/scan_task.py` and `app/business_logic.py`, and commit `403a355` states the
intent directly: "Restore `app/agents/company-auditor.py` as canonical source
for business_logic.py". The canonical sources are meant to be tracked; six of
seven are not. There is no backup and no history for the logic running in
production.

Planned action: **NO ACTION** — declared out of scope by the owner during this
audit. Recorded here because it is the single highest-risk finding.

### T1-5 · DEPLOYING.md's manual Step 3 could not deploy an agent at all

`rg-ai-agent-platform-docs/DEPLOYING.md:132-139` documented Step 3 exactly like
Steps 0-2:

    cd 3-rg-ai-agent-platform-agent
    bash setup.sh
    make doctor
    make setup
    make deploy

Steps 0, 1 and 2 work — those repos ship functional `setup.sh` scripts (verified
individually). The agent repo's does not: it exits 1 by design (T3-1). Anyone
following the documented manual path could not deploy an agent.

The supported mechanism, `bash manage-agent.sh add`, is already documented
elsewhere in the same file (`:81`, `:214`) — Step 3 simply never caught up.

Planned action: **DONE** — Step 3 repointed at `manage-agent.sh add`, with the
credential and redeploy follow-ups spelled out.

### T1-6 · An untracked `.tf` file can silently cross-contaminate agent IAM roles

`3-rg-ai-agent-platform-agent/daily-report-permissions.tf` — 116 lines,
**untracked and not gitignored**, simply never committed. Terraform loads every
`.tf` in the working directory, and this one attaches a policy to
`aws_iam_role.agent_task_role`, a resource that **every** agent's `main.tf`
defines. Its own header states the hazard:

> DO NOT leave this file present when running terraform plan/apply for any
> OTHER agent from the same reused working directory ... it will silently
> attach these CloudWatch-Logs-read + SES-send permissions to that OTHER
> agent's task role too.

The platform deploys every agent from this one reused directory
(`master-setup.sh`, `manage-agent.sh`, `redeploy-agent.sh` all stage into it),
so the hazardous condition is the normal condition. The only thing preventing
cross-contamination is remembering to move the file.

This directly contradicts the security control stated in `ARCHITECTURE.md`:
"Per-agent IAM isolation | Each agent has its own IAM task role with **no shared
permissions**". Because the file is untracked, it is also invisible to review,
to CI, and to every other clone.

Planned action: **ASK** — see T4-9. Not fixed here: any remedy changes IAM.

## Tier 3 — Redundancy / inefficiency

### T3-1 · `setup.sh` is a landmine — but deleting it is not the fix

`3-rg-ai-agent-platform-agent/setup.sh:5` prints "WARNING: THIS SCRIPT IS STALE
AND WILL NOT WORK CORRECTLY" and exits 1. Its body (lines 137-149) still
generates `external_secrets_arns` tfvars.

The audit brief suggested deleting it. **Investigation says do not.** It has
live referrers:

- `3-rg-ai-agent-platform-agent/Makefile:88,98,160,194` — four error messages
  telling the user to "Run: bash setup.sh"
- `rg-ai-agent-platform-docs/DEPLOYING.md:135` — Step 3 of the manual path
- `rg-ai-agent-platform-docs/TROUBLESHOOTING.md:15,17,87`

Deleting it turns five pointers into references to a missing file. As it stands
it is a guard that explains itself, which is strictly better.

The real defect it exposed is separate and worse — see T1-5.

Planned action: **NO ACTION** on the file itself; see T4-6 for the repair-or-remove
decision. Its downstream damage is fixed in T1-5.


### T3-2 · `trigger-e2e-test.yml` triplicated

Three near-identical copies, all differing only in a `triggered_by` string and a
path filter:

- `1-…-base/.github/workflows/trigger-e2e-test.yml` — 21 lines
- `2-…-orchestrator/.github/workflows/trigger-e2e-test.yml` — 20 lines
- `3-…-agent/.github/workflows/trigger-e2e-test.yml` — 20 lines

A reusable workflow (`workflow_call`) in one repo would remove two copies.

Blast radius: **moderate, and higher than it looks.** These are CI entry points
pinned to commit SHAs as a deliberate supply-chain control (`72faae1`,
`dd4f61a`). A cross-repo `workflow_call` introduces a new trust edge between
repos and would need the same SHA-pinning discipline. The duplication is 20
lines; the consolidation is a security-relevant change.

Planned action: **NO ACTION** — recommend leaving as-is. Cost of duplication is
lower than the cost of the new cross-repo dependency.

### T3-3 · Orchestrator `bootstrap.tf` fails `terraform fmt -check`

Two misaligned `tags` attributes, lines 48 and 67. Purely cosmetic whitespace.
`prod.tfvars` also fails in both orchestrator and agent repos, but is
**gitignored** in both and holds real customer values — deliberately not touched.

Planned action: **FIXING** — `bootstrap.tf` only.

## Tier 4 — Behavior changes to consider (no action taken)

### T4-1 · Uncommitted v2 work blocks two doc fixes

`3-…-agent` working tree carries 231 uncommitted lines across
`app/agents/company-auditor.py` (+185), `app/agents/company-auditor_scan_task.py`
(+39), and `app/scan_scaffolding.py` (+43) — a `TARGET_RECORD_IDS` manual-trigger
override. Fixing the stale headers in T2-4 would sweep this in-flight logic into
an audit commit. **Decision needed:** commit or stash the v2 work, then the
header fixes can land cleanly.

### T4-2 · Where should `CLAUDE.md` live?

Options: commit it to `rg-ai-agent-platform-docs` as the canonical copy and keep
the `§2a` / "working rule 8" numbering stable; or strip the cross-references from
the out-of-scope chat repo. Within this audit's scope the only citation is
`CUSTOMER-INSTALL-DEBUGGING.md:466`. Requires the file's actual contents.

### T4-3 · Changelogs — delete or mark unmaintained?

See T2-5. Either is defensible; both change what the repos claim about themselves.

### T4-4 · `hubspot-mapping.md` — adopt, relocate, or delete?

If it is to become authoritative, it belongs in `rg-ai-agent-platform-docs` and
needs regenerating from the deployed agents (requires `app/agents/` access). If
not, it should be deleted so it stops looking canonical.

### T4-5 · `destroy.sh:665` writes a dead variable

    external_secrets_arns  = []

into the tfvars it generates for teardown. Today this is a no-op that emits a
Terraform warning. Correcting it to `external_secrets = {}` is behavior-identical
— but `destroy.sh` is the most destructive script in the platform and this audit
declined to edit it unprompted.

### T4-6 · `setup.sh` — repair it or remove it and its five referrers?

Leaving a script whose entire job is to refuse to run is a papercut. Removing it
means also updating `Makefile:88,98,160,194` and `TROUBLESHOOTING.md:15,17,87`
to name the supported path. Repairing it means re-implementing agent tfvars
generation that `manage-agent.sh add` already does — probably not worth it.
Recommendation: remove it and repoint the six referrers. Not done unprompted
because it touches build tooling.

### T4-9 · How should `daily-report-permissions.tf` be contained?

See T1-6. Options, roughly in order of preference:

1. Move the file into a per-agent overlay directory that only that agent's
   deploy stages in — matches how `business_logic.py` and `scan_task.py` are
   already staged per agent (`redeploy-agent.sh:182,192`), so the pattern exists.
2. Guard it with a `count`/`for_each` on `var.agent_name == "daily-summary-report"`,
   making it inert for every other agent. Smallest change; keeps one directory.
3. Leave the manual procedure and commit the file so at least it is reviewable.

Whichever is chosen, it should be committed — an untracked file that grants IAM
permissions is not reviewable by anyone. Worth also confirming against live AWS
whether any agent other than daily-summary-report currently carries the
CloudWatch-Logs-read or SES-send policy, since a past deploy may already have
attached it. That check needs a valid AWS session, which was not available
during this audit.


## Explicitly not a problem — do not re-flag

These were checked this cycle and are correct. Recorded so the next audit does
not re-open them.

1. **`redeploy-*.sh` have not drifted.** All three source `redeploy-common.sh`
   (`redeploy-agent.sh:28`, `redeploy-chat.sh:37`, `redeploy-orchestrator.sh:28`).
   `redeploy-orchestrator.sh` carries no private copy of build/push/wait logic —
   its only matches are a comment (line 9) and a log-tail hint (line 191). Its
   older mtime reflects stability, not staleness.
2. **SSM `ignore_changes` coverage is complete.** `orchestrator_system_prompt`
   (`2-…/bootstrap.tf:18`, lifecycle at 50-51) and `orchestrator_agent_routing`
   (`:57`, lifecycle at 68-69) both have `ignore_changes = [value]`. The agent
   repo's `external_api_endpoint` (`3-…/bootstrap.tf:23`) has it too.
3. **Customer-name genericity is fine *in the docs repo's scripts*.** Exactly one
   `asknicely` string exists in its tracked `.sh`/`.md` files — `destroy.sh:310`,
   "The 2026-08-04 AskNicely destroy test proved..." — a dated historical note
   where the specific customer is the point. **This item was originally scoped too
   narrowly**: it grepped only that repo's scripts and docs. A full sweep of all
   tracked files in all six repos found a real problem — see T4-10.
4. **`scan_task.EXAMPLE.py` is not a dangling reference.** It appears absent from
   GitHub but exists on disk; it is untracked, part of T1-4, not a broken link.
5. `deal-auditor`'s non-sequential criterion properties (`__f2 … __a2`, `__7 … __23`,
   `__50`) are deliberate. Do not normalize.
6. `deal-auditor`'s non-uniform deal-stage groups, and criterion 1 being assessed
   but excluded from the stage grid, are deliberate (legacy sheet `F2:J8` range).
7. The evidence window's `last_forecast_date` minus 7-day buffer is deliberate.
8. `OrchestratorAuditLog.log()` taking `company_id=` for every record type is an
   intentional schema-uniformity decision. An alias may be *proposed* with a
   migration path; it must not be changed unilaterally.
9. `AgentClient` retrying only `httpx.ConnectError` and never
   `httpx.TimeoutException` is deliberate — a timeout may occur after the agent
   has begun mutating CRM data. **Never widen this retry.**
10. HubSpot date properties rendering a day early in Central time is accepted
    HubSpot behavior (midnight-UTC storage), not an agent bug.
11. **The agent README's `us-east-1` examples are correct.** `install.sh:363`
    falls back to `us-east-1`; they are generic-template defaults, not a stale
    reference to AskNicely's `us-east-2`.
12. **Every "five repositories" claim is correct.** See T2-2 — verified
    occurrence by occurrence, not swept.

## Unverified

Stated as unverified rather than guessed:

- **Timeout consistency** (agent `CLAUDE_TIMEOUT` / `timeout_seconds` vs. the
  orchestrator's per-agent `agent_timeouts` vs. the 60s default). The agent-side
  values live in `app/agents/`, which was out of scope. Not checkable statically
  from the orchestrator side alone.
- **Forced-tool-use output handling** (direct subscripting of model tool output
  instead of `.get()` with a logged fallback). Requires reading every LLM-using
  agent in `app/agents/`. Only `deal-auditor`'s `_normalize_assessment()` fix is
  known, by report rather than by inspection.
- **HubSpot client duplication across agents**, and duplication between
  `<agent>.py` and `<agent>_scan_task.py`. Same scope exclusion.
- **`terraform validate`** was not run. It requires `terraform init`, and the
  audit avoided any initialization step against repos wired to remote state.
  `terraform fmt -check` was run everywhere and is reported in T3-3.
- **`defaults.env.example`** — confirmed absent, but whether that is intentional
  (the file holds customer secrets and is generated by `install.sh`) was not
  established.
- **CI secret-scanning claims** in `docs/security/supply-chain-controls.md`
  ("a full-history sweep of all five repositories has been run clean") were not
  re-run against the sixth repo.
